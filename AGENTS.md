# ProjectWiki: правила работы

## Репозитории и данные
- Основной репозиторий приложения — `dmandr/projectwiki`, публичный форк Gollum. Сохраняем исходную историю, изменения делаем поверх неё. `origin` — наш репозиторий, `upstream` — Gollum.
- Документы, изображения, PDF и прочие пользовательские данные живут в отдельном репозитории книги. Никогда не копируйте их, приватные настройки и секреты в публичный репозиторий приложения.
- `dmandr/projectbook-testwiki` — отдельная одноразовая тестовая книга. Пользователь разрешил свободно менять её содержимое, делать commit и push без отдельного подтверждения. Это исключение не распространяется на приложение или исходную Trinity.

## Обязательный цикл изменений приложения
1. Сначала проверяем текущее состояние репозитория и согласуем план; не начинаем весь backlog автоматически.
2. Реализуем согласованный шаг локально.
3. Собираем и разворачиваем в локальном Docker, проверяем поведение на тестовых документах. Проверки выбираем по рискам изменения.
4. Даём пользователю работающий URL, описание изменений и результаты проверок, чтобы он мог посмотреть и попробовать.
5. Только после явного подтверждения пользователя делаем commit и push изменений приложения, включая документацию и конфигурацию. До этого оставляем их незакоммиченными.
- Не запрашиваем повторное разрешение на уже согласованную реализацию и локальное тестирование.
- Не останавливаем используемые экземпляры и не сбрасываем несохранённую работу пользователя. Для нового варианта используем отдельный порт и при необходимости отдельный clone книги.
- Для проверки синхронизации два экземпляра должны иметь разные локальные clone одного remote, а не один общий рабочий каталог.

## Архитектура и поставка
- Git и обычные Markdown/медиа-файлы — источник истины; отдельная обязательная база данных не нужна.
- Предпочитаем штатные расширения MDXEditor; его форк — только при доказанном ограничении.
- Запись документов, вложений, TODO и синхронизация должны согласовываться единым механизмом работы с репозиторием.
- Не используем автоматические force push и переписывание общей истории как способ синхронизации.
- Docker-конфигурация, запуск, остановка, очистка, настройки и проверка результата должны быть воспроизводимы и описаны в репозитории. Данные книги сохраняются вне контейнера.
- Внешнее размещение и домены — отдельный этап, сначала локальный Docker.

## Коммуникация
- Общаемся по-русски. Согласованные требования и решения сохраняем в документации; ближайший план — `PLAN.md`.
- Чётко различаем реализованное и предложенное. Не заявляем, что remote автоматически обеспечивает синхронизацию или пользовательскую авторизацию Web UI.
